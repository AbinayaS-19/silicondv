Verification term of the day

Observability

How easily an internal behavior can be seen at an output, monitor or checker. If a bug happens but nothing notices, you do not have enough observability.

A beginner’s guide to design verification.

If you are new to the field, work through these modules in order. Learn enough to build one small testbench, then return to the earlier lessons with the questions that practical work brings.

  1. What verification engineers actually do

    Begin with the job

    Design engineers build the RTL. Verification engineers build the evidence that the RTL behaves as intended, including at boundaries and under failure conditions. The role exists because a design can compile and still be wrong.

    1. Learn how a requirement becomes a verification plan.
    2. Separate stimulus, observation, checking and coverage.
    3. Understand the difference between a design bug and a testbench bug.
    ExampleA FIFO write on the same cycle as reset is not just a corner case. The specification must say which action wins.
    Common mistakeWriting tests before deciding what the checker can actually observe.
    PracticeTake one page of a specification and list five behaviors, three boundaries and two unanswered questions.

  2. Digital design foundations

    Read the hardware first

    You need enough digital design knowledge to predict what the DUT should do. Start with the behavior you can see at a clock edge, not transistor physics.

    1. Boolean logic, combinational logic and sequential logic.
    2. Flip flops, registers, counters and finite state machines.
    3. Clocks, reset, setup and hold, latency and throughput.
    4. Basic buses, valid and ready handshakes, FIFO empty and full behavior.
    ExampleIf valid stays high while ready is low, the payload normally has to remain stable until the transfer happens.
    Common mistakeTreating a waveform as decoration instead of tracing state one clock edge at a time.
    PracticeDraw a four cycle handshake by hand and mark exactly when the transfer is accepted.

  3. SystemVerilog for verification

    Learn the language in context

    SystemVerilog is both a design language and a verification language. For DV, learn the parts that help you represent transactions, generate varied stimulus and coordinate concurrent work.

    1. Types, arrays, queues, structs and interfaces.
    2. Tasks, functions, classes and object handles.
    3. Processes, events, mailboxes and clocking blocks.
    4. Randomization, constraints and why a legal random space matters.
    ExampleA queue makes sense for an ordered stream of transactions because its size can grow and items can be popped in order.
    Common mistakeJumping into classes before understanding blocking, nonblocking and event scheduling.
    PracticeModel a packet with a class, constrain its length and print ten legal variations.

  4. Testbench thinking

    Build a checking loop

    Before UVM, write one small testbench. Drive known inputs, observe the output and compare it with an expected result. This makes the later UVM structure feel necessary instead of ceremonial.

    1. Write a test plan from a small specification.
    2. Create a transaction and a simple reference model.
    3. Drive the interface and monitor what the DUT accepted.
    4. Make failures clear enough that another engineer can debug them.
    ExampleFor an adder, generate operands, predict the sum independently and report the inputs with every mismatch.
    Common mistakeCalling a test successful because the waveform looks reasonable.
    PracticeVerify a counter with reset, enable, wraparound and one deliberately broken RTL version.

  5. UVM from scratch

    Structure first, then behavior

    UVM organizes work you already understand. Learn it in the order one transaction moves through the bench, not as a list of class names.

    1. Test and environment: the test chooses the scenario and configuration. The environment owns reusable agents, scoreboards and models.
    2. Agent: group a sequencer, driver and monitor for one interface. A passive agent keeps the monitor but does not drive.
    3. Sequence path: a sequence creates an item, the sequencer arbitrates it and the driver converts it into pin activity.
    4. Observation path: the monitor reconstructs what the DUT accepted and publishes transactions through an analysis port.
    5. Checking path: the scoreboard predicts, aligns and compares results. RAL models register intent and mirror observed state.
    6. Build phase: create components with the factory and read configuration.
    7. Connect phase: wire transaction paths after every endpoint exists.
    8. Run phase: advance time, drive traffic, observe responses and manage objections from the test or virtual sequence.
    ExampleA monitor should report what the DUT accepted, not what the driver hoped it sent. If ready is low, the monitor should not publish the transaction yet.
    Common mistakeStarting a sequence successfully and assuming the driver received the item. Trace start_item, finish_item, get_next_item and item_done.
    PracticeDraw sequence, sequencer, driver, interface, monitor and scoreboard. Label each TLM connection and the owner of every objection.
    Continue here:Open the complete UVM learning guide

  6. SystemVerilog assertions

    Make timing rules executable

    Assertions are compact checkers for behavior over time. Start by turning one English sentence into a trigger, a timing window and a required response.

    1. Immediate and concurrent assertions.
    2. Sequences, properties and sampled values.
    3. Overlapped and nonoverlapped implication.
    4. Delay ranges, repetition and reset with disable iff.
    Example“Request implies grant within three cycles” needs a precise decision about whether the current cycle counts.
    Common mistakeWriting one giant property that fails without telling you which rule broke.
    PracticeTranslate three English timing rules, then fail each property on purpose.
    Recommended:Top 5 SVA questions and answers in the interview hub

  7. CDC basics

    Preserve information across clocks

    A clock domain crossing problem is not only about metastability. The destination must receive the same information the source intended to send.

    1. Understand metastability and why simulation alone cannot model it fully.
    2. Use a synchronizer for a stable single bit level.
    3. Use a pulse, toggle or handshake scheme for events.
    4. Use an asynchronous FIFO for a data stream.
    5. Learn why multi bit reconvergence needs separate attention.
    ExampleA slow destination can miss a one cycle pulse even when metastability is handled.
    Common mistakeAdding two flops to every crossing without asking what information must survive.
    PracticeClassify a level, pulse, counter and data stream, then choose a structure for each.

  8. Functional coverage and signoff

    Ask whether the evidence is enough

    Coverage tells you what your tests exercised. It does not prove correctness by itself. Use it with assertions, checking, code coverage and bug review to decide what remains unknown.

    1. Write coverpoints for behaviors in the verification plan.
    2. Add crosses only when the combination has meaning.
    3. Classify holes as stimulus, observability, model, unreachable or design gaps.
    4. Review checks, coverage, bugs and waivers before signoff.
    ExampleA missed bin may mean the stimulus never reached a legal case, or that the bin itself describes something impossible.
    Common mistakeTreating 100 percent as proof that every checked behavior is correct.
    PracticePick five coverage holes and classify each before changing a constraint.

  9. Interview preparation

    Explain your reasoning out loud

    An interview answer is stronger when you can explain why a method exists, where it fails and how you would debug it. Practice on paper and speak through one transaction from sequence to scoreboard.

    1. Review digital design and SystemVerilog fundamentals.
    2. Draw UVM data flow and phase order without notes.
    3. Write one assertion from an English requirement.
    4. Explain one real debug method from first failure to root cause.
    5. Answer with a small example, then name the tradeoff.
    ExampleFor every “what is” question, add a “when would you use it” and a “what can go wrong.”
    Common mistakeReciting a definition and stopping before the interviewer can hear your judgement.
    PracticeRecord a two minute answer, listen once and remove every sentence that does not help the reasoning.

III
A worked example

Turning one requirement into a useful test.

Take a requirement such as “a full FIFO must reject writes without corrupting stored data.” I do not begin by opening a sequence file. I first turn that sentence into four things I can reason about: the starting state, the action, the visible response and the state that must not change.

The phrase “reject writes” is not precise enough on its own. Does the interface lower ready, raise an error or accept the handshake and discard the data? Does the full flag rise on the same edge as the final legal write or one cycle later? Those questions belong in the specification discussion, not in a guess hidden inside the scoreboard.

The concrete test

Use a depth four FIFO and write A, B, C and D. Check that full asserts at the specified time. While full, attempt to write X. Then read four entries and expect A, B, C and D in order, followed by empty. X must never appear, and neither pointer may advance for the rejected transfer.

If it fails

Start at the first bad cycle. If the write pointer moved, the acceptance rule is wrong. If the pointer stayed still but a later read returns X, inspect the memory write enable. If data is correct but full is late, the flag calculation may use stale pointer state. One requirement can expose several distinct bugs.

Name the behaviorA write attempted while full must not become a stored transaction.Question to ask: what exact interface event counts as an attempt?

Control the preconditionFill the FIFO to its declared capacity with recognizable values.Example: A, B, C and D make ordering errors obvious.

Apply one meaningful actionAttempt one additional write and keep all unrelated controls quiet.Changing only one thing makes the result easier to diagnose.

Check response and invariantsCheck the interface response, pointer stability, occupancy and eventual readback.The full flag is one observation, not the whole proof.

Record the evidenceCover full with a write attempt and assert that rejected writes do not change state.Also retain the directed readback because it checks data integrity.

Key takeaway: a good test proves both the visible response and the invariants behind it. If the requirement leaves cycle timing or acceptance semantics unclear, resolve that before encoding the answer in the testbench.

DV core interview questions

These questions are less about recalling definitions and more about showing how you make a verification decision. A useful answer starts with the requirement, names the checker or stimulus mechanism and finishes with the evidence you would inspect.

Try this: explain reset during traffic for a request and response interface. State what happens to an accepted request, how the monitor recognizes reset and how the scoreboard removes stale expectations.

Keep: definition, example, tradeoff and debug step. That four part answer is usually stronger than a long list of terms.

Classify a coverage hole

An uncovered bin is a question, not an instruction to run more seeds. The scenario may be legal but ungenerated, generated but invisible, impossible by design or missing because the RTL cannot reach the intended state.

Try this: if full and simultaneous read plus write is uncovered, first prove the FIFO reached full, then confirm the monitor sampled both controls on the acceptance edge. Only after that should you change stimulus.

CDCStructures

Choose the crossing by information type

The crossing structure depends on what must survive: a stable level, a brief event, a related group of bits or an ordered stream. A pair of synchronizer flops addresses metastability risk for a sampled control, but it does not preserve every kind of information.

Try this: send a one cycle source pulse into a slower destination clock. If no destination edge sees the pulse, two flops cannot recover it. A toggle or handshake carries the event instead.

Interview practice that tests how you think.

A strong answer is not a wall of terminology. I listen for a clear model, one useful example and an honest tradeoff. These are the questions I would use to practise that habit.

When should a check live in an assertion, a scoreboard or both?

I use an assertion when the rule is local in time and tied closely to an interface or protocol. “Grant arrives within three cycles of request” is a good assertion. I use a scoreboard when the expected result needs state, ordering or a reference model.

Sometimes both are right. The assertion checks that the protocol stayed legal while the scoreboard checks the end result. I would say that out loud, then give one failure each checker can catch.

How would you verify reset in the middle of active traffic?

I would first ask what the specification promises. Are outstanding transactions dropped, replayed or completed? Which outputs must change immediately and which change on a clock edge?

Then I would reset at different points in a transaction, check state cleanup, confirm no stale response escapes and verify the first legal transaction after reset. The common mistake is checking only that registers become zero. Reset is a behavior, not just a value.

A random regression fails once in one thousand seeds. What do you do first?

I preserve the seed, tool version, configuration and first failing message before changing anything. Then I reproduce the smallest failing run and work backwards from the first bad observation, not from the final scoreboard complaint.

I also compare the failing and passing traces near the divergence. Adding debug everywhere too early can make the failure slower to understand. One precise hypothesis at a time usually wins.

What does 100 percent functional coverage prove?

It proves that every modeled bin was sampled. That is useful, but it does not prove the model was complete, the checker was correct or the design behaved properly when the bin was hit.

I would review the coverage model against the verification plan, look at meaningful crosses, inspect assertion results and close known bug and waiver questions. A full dashboard can still hide a weak argument.

How do you debug a scoreboard mismatch?

I start with the earliest mismatch and ask four things: was the input transaction observed correctly, did the reference model predict the right value, did the output monitor sample the right cycle and did the queue preserve ordering?

Only then do I blame the DUT. Scoreboards are excellent at reporting disagreement, but they do not automatically tell us which side is wrong. That distinction matters in real debug.

DV fundamentals

How do you turn a specification into a verification plan?

I start with observable behavior, not test names. For every requirement I write the precondition, the accepted action, the expected response, the timing window and the state that must remain unchanged. Then I decide whether stimulus, an assertion, a scoreboard or coverage is the right evidence.

For a depth four FIFO, “reject a write while full” becomes a fill sequence, one extra write attempt, a stable pointer check, four ordered reads and a coverage point for the attempted overflow. I also record open questions instead of hiding an assumption in the reference model.

Common follow upHow do you know the plan is complete? Trace every requirement to at least one check and one coverage item, then review boundaries, reset and simultaneous events.
Mistake candidates makeListing directed test names without saying what each test proves. A long list is not a verification strategy.

Interview tip: take one small requirement and walk it all the way from intent to evidence. That shows more judgement than naming five methodologies.

What is the difference between a testbench bug and a design bug?

A mismatch only proves disagreement. I separate the paths. First I confirm that the monitor sampled the accepted input correctly. Then I check the reference model, expected queue, output sampling and comparison timing. If the independent expectation is sound and the DUT diverges, I have a design bug. If the expectation or observation is wrong, I have a testbench bug.

Suppose a scoreboard reports the wrong FIFO data. The RTL may have reordered entries, but the monitor may also have sampled on the wrong edge or the scoreboard may have popped the expected queue before a real read handshake.

Common follow upWhat evidence would you save? The seed, first mismatch, accepted input history, expected queue state and a narrow waveform around the first divergence.
Mistake candidates makeBlaming the DUT because the scoreboard printed an error. The checker is code too.

Interview tip: say “first bad cycle” early. It tells the interviewer that you debug causes rather than symptoms.

02 / 07

SystemVerilog

When do you use blocking and nonblocking assignments in a testbench?

I use blocking assignments for sequential software style calculation inside a task or function when each statement should see the previous result immediately. I use nonblocking assignments for clocked signal updates when I want the value scheduled without creating a race with other processes on the same edge.

In a driver, I prefer a clocking block and write through its outputs. That makes the sampling and driving skew explicit. The answer is not simply “blocking for combinational and nonblocking for sequential” because testbench code also depends on simulator regions.

Common follow upWhat problem does a clocking block solve? It gives the testbench a defined relationship between sampling, driving and the clock event.
Mistake candidates makeRepeating an RTL rule without discussing races between the DUT, driver and monitor.

Interview tip: draw one rising edge and say when the DUT samples, when the driver updates and when the monitor observes.

What makes a constrained random test useful?

A useful constraint describes the legal space while keeping important boundaries reachable. Randomness is only a stimulus strategy. It becomes valuable when coverage tells me which legal behaviors were exercised and when the seed makes a failure repeatable.

For a packet length from one to 64 bytes, I may keep every value legal but bias the distribution toward one, two, 63 and 64. I still inspect the sampled distribution because a solver can satisfy my code while my intent remains underrepresented.

Common follow upHow do you debug a randomize failure? Isolate the active constraints, inspect conflicting relationships and reduce the object to the smallest unsatisfied set.
Mistake candidates makeOverconstraining the stimulus until only normal traffic remains, then calling the regression comprehensive.

Interview tip: mention legality, distribution, reproducibility and coverage. Those four words show you understand the whole loop.

03 / 07

UVM

Walk one transaction from a sequence to the scoreboard.

The sequence creates and randomizes an item, then sends it through the sequencer. The sequencer arbitrates between active sequences. The driver gets the item, converts it into pin activity and calls item_done only when it has finished consuming that item.

The monitor independently samples the interface and publishes the transaction through an analysis port. A predictor or scoreboard receives it, updates expected state and compares the observed response. I keep the monitor independent because the scoreboard should check what the DUT accepted, not what the sequence intended.

Common follow upWhere does a response go? The driver can return a response item through the sequencer when the sequence needs protocol level feedback.
Mistake candidates makeConnecting the scoreboard directly to the driver and losing an independent observation path.

Interview tip: draw arrows while you answer. Name the request path and observation path separately.

Why use the factory and configuration database?

The factory lets a test replace a registered type without editing the reusable environment. I use it for controlled variation, such as substituting an error injecting driver or a specialized sequence item. The configuration database passes settings or handles down the hierarchy without hard coding a parent reference into every child.

For example, the top level sets a virtual interface for uvm_test_top.env.agent*, and the driver and monitor retrieve it during build. I keep paths narrow because a wildcard that reaches too much of the bench can create hidden coupling.

Common follow upWhy might an override fail? The class was not registered, the requested type was created with new, or the instance path did not match.
Mistake candidates makeUsing the configuration database as a global variable store and making ownership impossible to trace.

Interview tip: give one reason to use each mechanism and one reason not to overuse it.

04 / 07

SystemVerilog assertions

What is the difference between overlapped and nonoverlapped implication?

With |->, the consequent begins on the same sampled cycle where the antecedent completes. With |=>, it begins on the next sampled cycle. I do not choose from memory alone. I draw the trigger and the earliest legal response.

If valid and ready must never be high together, same cycle checking fits overlapped implication. If a request sampled on cycle ten requires grant from cycle eleven onward, nonoverlapped implication is clearer.

Common follow upHow does a delayed consequent change the timing? Combine the implication start point with the delay, then count cycles on paper.
Mistake candidates makeChoosing an operator before deciding whether the current cycle belongs in the allowed window.

Interview tip: answer with cycle numbers. They remove ambiguity immediately.

How do you know an assertion did not pass vacuously?

An implication can pass because its trigger never occurred. I add coverage for the antecedent and for a successful complete match, then review whether those cover properties were reached in the intended tests.

For request followed by grant, a green assertion is weak evidence if request stayed low for the whole run. I want at least one covered request and one covered legal grant response, plus a negative test that makes the assertion fail on purpose.

Common follow upWould assertion coverage alone prove the property is correct? No. I still review boundary traces and confirm the property fails on the intended violation.
Mistake candidates makeReporting a zero failure count without checking that the antecedent had a chance to fire.

Interview tip: say how you would test the checker itself. That is the part many answers miss.

05 / 07

Clock domain crossing

Why is a two flop synchronizer not enough for every crossing?

It reduces the probability that metastability propagates when a destination samples one stable control level. It does not guarantee that a short pulse is sampled, preserve the relationship between several bits or carry an ordered stream.

A one cycle pulse from a fast source can disappear between slow destination edges. I would use pulse stretching, a toggle or a handshake depending on event rate. For payload streams, I would use a handshake or asynchronous FIFO instead of synchronizing each data bit independently.

Common follow upWhy not synchronize every bus bit? Each bit can settle in a different cycle, so the destination may see a value the source never produced.
Mistake candidates makeTreating every CDC failure as metastability and ignoring loss, duplication and incoherent data.

Interview tip: begin by classifying the information: level, event, related control or ordered payload.

How would you verify an asynchronous FIFO?

I vary the clock ratio and phase, exercise independent resets and generate bursts that cross empty and full boundaries. The scoreboard tracks accepted writes in source order and accepted reads in destination order. I check no loss, duplication or reordering.

I also verify pointer and flag behavior around wraparound, then use CDC analysis for synchronizer structure and assertions for local protocol rules. Simulation alone cannot model analog metastability, so I do not claim that a random clock test proves physical safety.

Common follow upWhy use Gray coded pointers? Only one bit should change between adjacent values, which reduces incoherent sampling risk across the domain boundary.
Mistake candidates makeRunning two different clocks and calling that CDC verification without checking information preservation.

Interview tip: separate structural CDC checks from functional data integrity checks.

06 / 07

Coverage and closure

What is the difference between code coverage and functional coverage?

Code coverage reports which RTL structures executed, such as statements, branches, expressions or toggles. Functional coverage reports whether the behaviors named in the verification plan were observed. They answer different questions and neither proves correctness alone.

A FIFO test may toggle every RTL branch while never attempting a write at full. Code coverage looks healthy, but the requirement level behavior is missing. The reverse can also happen when the functional scenario is covered but dead or unintended RTL remains untouched.

Common follow upWhich one do you close first? I use both together and investigate holes by risk, not by one fixed percentage order.
Mistake candidates makeSaying functional coverage is always better. It is only as good as the model and sampling.

Interview tip: name the question each metric answers instead of arguing that one replaces the other.

How do you close a stubborn coverage hole?

I classify it before changing stimulus. Was the scenario generated? Was it accepted by the interface? Did the monitor sample it? Is the bin legal and reachable? Did the RTL fail to enter the intended state?

If a full FIFO read and write cross is empty, I inspect the trace in that order. The fix might be a focused sequence, a monitor correction, a repaired bin, a design bug or a documented exclusion. More seeds are only useful when probability is actually the problem.

Common follow upWhen is a waiver reasonable? When the condition is proved unreachable or intentionally excluded and the rationale is reviewed and recorded.
Mistake candidates makeChanging constraints immediately and accidentally disturbing scenarios that were already well covered.

Interview tip: use the words generated, accepted, observed and sampled. That sequence gives your answer structure.

07 / 07

Tricky scenarios

A valid and ready interface stalls for twenty cycles. How do you decide whether it is a bug?

I first read the protocol contract. If ready may stay low without a latency bound, the stall may be legal even when it is undesirable. I check that valid and payload remain stable while blocked, no transfer is counted before both are high and the eventual transfer happens exactly once.

If the specification promises progress within a bound, I add or inspect a liveness property. I also separate local backpressure from system deadlock by tracing the reason ready stayed low through downstream queues and credits.

Common follow upWhat would you assert? Stability while valid is high and ready is low, plus bounded progress only if the architecture promises it.
Mistake candidates makeCalling any long stall a protocol violation without checking whether the contract includes a progress guarantee.

Interview tip: do not invent a requirement. Say what must be clarified before you label the behavior.

The test passes alone but fails in a regression. What do you investigate?

I preserve the regression command, seed, order, tool version and configuration. Then I look for shared state, uninitialized values, timing assumptions, test order dependence and resource collisions. A passing standalone replay can mean the original environment changed the starting conditions.

I compare the earliest divergence between a passing and failing run. If the failure depends on another test, I inspect static variables, global configuration, files, reset cleanup and anything that survives longer than the test expects.

Common follow upWould you add a delay to make it pass? No. A delay can hide a race without explaining it. I want a synchronization rule or ownership fix.
Mistake candidates makeRerunning until green and treating the failure as noise.

Interview tip: distinguish reproducibility from frequency. A rare failure still has a deterministic cause in the simulated system.

Architecture, piece by piece

Each component should have one clear job. If a class drives, observes, predicts and checks at once, reuse and debug both become harder.

Test

Selects the scenario, configures the environment, applies overrides and starts top level sequences. The test should express intent, not contain pin level driving.

Interview check: what changes between two tests if the environment is reusable?
Environment

Owns reusable agents, scoreboards, coverage collectors, virtual sequencers and reference models. It connects block level pieces into one verification system.

Common confusion: the environment is structure. The test chooses how that structure is used.
Agent

Packages one interface. An active agent has a sequencer, driver and monitor. A passive agent keeps only the observation side.

Example: a block bench drives AXI actively but watches a status interface passively.
Driver

Consumes sequence items and converts them into timed interface activity. It owns the protocol handshake and must not call item_done before it has finished the item.

Common mistake: treating delay and reset behavior as sequence responsibilities.
Monitor

Samples the interface, reconstructs accepted transactions and publishes them. It should not trust the driver or drive any signal.

Example: publish a valid and ready transfer only on the clock edge where both are sampled high.
Sequencer

Arbitrates between sequences and provides the request and response channel to the driver. It does not create pin activity.

Common confusion: the sequencer is not the stimulus generator. Sequences generate transaction intent.
Sequence

Creates and randomizes items, controls their order and can coordinate scenarios across agents through a virtual sequence.

Keep protocol timing in the driver unless the transaction abstraction genuinely includes timing.
Scoreboard

Builds or receives an independent expectation, aligns it with observed output and reports differences with enough context to debug.

A scoreboard mismatch means disagreement. It does not automatically mean the DUT is wrong.
RAL model

Represents registers, fields, access policies and mirrored state. An adapter translates between register operations and bus items. A predictor updates the model from observed traffic.

Use the mirror as a model of expected state, not as proof that the hardware matches it.
02 / 08

Build, connect and run

The phase names matter less than the responsibility boundary. Build creates. Connect wires. Run consumes simulation time.

Build phase

Create child components through the factory and read configuration that decides structure or behavior.

  • The parent builds before its children.
  • Use type_id::create for components.
  • Get the virtual interface and agent activity setting here.
  • Do not start timed stimulus here.

Connect phase

Join endpoints after the hierarchy exists. This is where structural communication becomes explicit.

  • Connect driver and sequencer.
  • Connect monitor analysis ports to subscribers.
  • Connect register predictor and adapter paths.
  • Print topology if an endpoint receives nothing.

Run phase

Clocks move, sequences run, drivers wait for items and monitors collect activity. Objections control when the test may finish.

  • Raise an objection before starting the scenario.
  • Drop it after expected drain and checking finish.
  • A blocked forever task does not keep simulation alive by itself.
  • Keep objection ownership small and obvious.

What actually happens

UVM walks the component tree through build. By connect, all expected children should exist, so ports can point to real exports or implementations. Run phase tasks then execute concurrently. If a scoreboard is missing, run phase cannot repair the hierarchy. If a monitor exists but has the wrong virtual interface, stimulus can run while observation remains silent.

Practical tip: call uvm_top.print_topology() before the first complicated test. Save the known good topology and compare it when configuration changes.

function void build_phase(uvm_phase phase);
  super.build_phase(phase);
  sqr = bus_sequencer::type_id::create("sqr", this);
  drv = bus_driver::type_id::create("drv", this);
  mon = bus_monitor::type_id::create("mon", this);
endfunction

function void connect_phase(uvm_phase phase);
  super.connect_phase(phase);
  drv.seq_item_port.connect(sqr.seq_item_export);
  mon.ap.connect(env.scoreboard.actual_imp);
endfunction
03 / 08

Sequence and sequencer communication

The handshake protects item ownership. Learn the request path before using convenience macros.

The sequence side

start_item(req) waits until the sequencer grants this sequence permission to send. Randomize or fill the request after that grant if arbitration timing matters. finish_item(req) sends the prepared request and waits until the driver completes it.

The driver side

get_next_item(req) obtains the request. The driver performs the complete protocol operation, then calls item_done(). If a response matters, the driver creates a separate response, preserves the transaction identity and returns it through item_done(rsp) or put_response.

Common bug: forgetting item_done leaves the sequence waiting forever. Calling it too early lets the next item arrive before the driver is ready.

// Sequence
req = bus_item::type_id::create("req");
start_item(req);
if (!req.randomize() with { write == 1; })
  `uvm_fatal("RAND", "Request randomization failed")
finish_item(req);

// Driver
seq_item_port.get_next_item(req);
drive_request(req);
wait_for_accept();
seq_item_port.item_done();
Sequence versus sequence item

The item is transaction data. The sequence is procedural control that creates and orders items.

Sequencer versus driver

The sequencer arbitrates requests. The driver knows the interface timing and moves the pins.

Virtual sequence versus virtual sequencer

A virtual sequence coordinates child sequencers. A virtual sequencer is an optional holder of those handles. Many benches can coordinate directly through handles in the virtual sequence.

04 / 08

TLM ports without the fog

Transaction level modeling lets components communicate with objects instead of reaching into one another.

Port

A component calls an interface method through a port. The driver sequence item port is the familiar request side example.

Think: I need a service.
Export

An export forwards an interface implementation through hierarchy. The sequencer exposes its sequence item export to the driver.

Think: I expose a service implemented below or elsewhere.
Implementation

An implementation provides the method body. A scoreboard analysis implementation receives transactions through its write method.

Think: this class performs the service.
Analysis port

A publisher calls write once and every connected subscriber receives the transaction. Monitors use this broadcast pattern.

Important: subscribers should clone if they retain or modify the object.
FIFO

A TLM analysis FIFO buffers published transactions and gives the consumer a blocking or nonblocking retrieval interface.

Useful when producers and consumers run at different rates.
Connection debug

If nothing arrives, verify the producer calls write, inspect connection count, confirm the correct instance path and print the transaction before and after publication.

Do not start by rewriting the scoreboard.
05 / 08

Factory and configuration

Both mechanisms support reuse, but they solve different problems. The factory changes type. Configuration changes a value or passes a handle.

Factory

Register reusable classes, create them through type_id::create and apply an override before the target instance is built. A type override replaces every matching requested type in scope. An instance override targets a hierarchy path.

Configuration database

Set a value from a known owner and get it in the component that needs it. Virtual interfaces, active or passive mode and small policy objects are reasonable uses. Narrow paths make intent visible. Wildcards make demos quick but large benches hard to reason about.

Debug order: print the topology, print factory overrides, check the exact instance path and fail immediately when a required get returns false.

// Top level before run_test
uvm_config_db#(virtual bus_if)::set(
  null, "uvm_test_top.env.agent*", "vif", bus_vif
);

// Driver build phase
if (!uvm_config_db#(virtual bus_if)::get(
      this, "", "vif", vif))
  `uvm_fatal("NOVIF", "bus_if was not configured")

// Test build phase
base_driver::type_id::set_inst_override(
  error_driver::get_type(), "env.agent.drv", this
);
06 / 08

Register abstraction layer

RAL gives register intent one model, but it still needs a real bus path and a reliable observation path.

Register model

Describes blocks, registers, fields, addresses, reset values and access policies. Build and lock it before use.

Interview question: what is modeled that a raw bus transaction does not know?
Adapter

Converts a generic register operation into the bus sequence item and converts a bus response back.

A wrong byte enable or response mapping can make good RTL look broken.
Map and sequencer

The map holds address and access information. Connecting it to the bus sequencer and adapter enables front door operations.

Front door uses the interface. Back door accesses the modeled HDL path directly.
Predictor

Consumes monitored bus transactions and updates mirrored values. Explicit prediction is useful when traffic comes from more than RAL itself.

Predict from observation, not merely from the requested write.
Desired and mirrored values

The desired value is what the model wants. The mirrored value is what the model believes is currently in the DUT.

Neither replaces an actual read when hardware side effects may change state.
Common register bugs

Check reset values, read only and write one to clear behavior, volatile fields, aliasing, access size and side effects.

Do not stop after a simple write then read test.
07 / 08

A bring up order that saves time

I bring up one path at a time. A complicated random test is the last thing I add, not the first.

Prove structure

Print topology. Confirm every expected component, activity setting and virtual interface. Check factory overrides before simulation behavior gets involved.

  • One active agent
  • One driver and sequencer connection
  • One monitor publication path

Prove one transfer

Use one directed item. Log when it is created, granted, driven, accepted, observed and compared. The same transaction should tell one consistent story.

  • No random timing yet
  • No parallel sequences yet
  • No hidden retry behavior

Add pressure carefully

Add reset, backpressure, overlap and randomization one dimension at a time. Preserve the first failing seed and remove noise around the earliest divergence.

  • Check drain before dropping objections
  • Make errors carry transaction context
  • Fail required configuration early
“The sequence drives the interface.”

Correction: the sequence describes transaction intent. The driver owns pin level timing.

“The monitor can reuse the driver item.”

Correction: the monitor reconstructs an independent item from sampled interface activity.

“An objection starts or stops clocks.”

Correction: an objection only tells the phase scheduler that useful work is still in progress.

“More hierarchy means more reuse.”

Correction: reuse comes from clear responsibilities and stable transaction boundaries, not from adding layers.

“A scoreboard must compare immediately.”

Correction: the scoreboard must align expected and actual transactions according to protocol ordering and latency.

08 / 08

How UVM maps to interview questions

Do not stop at definitions. For each topic, explain one failure it prevents and one way you would debug it.

Architecture

Draw test, environment, agent and scoreboard. Then trace one transaction through the request and observation paths.

Phases

Explain why creation belongs in build, wiring belongs in connect and timed activity belongs in run.

Sequence handshake

Describe start_item, finish_item, get_next_item and item_done, including the deadlock when completion is forgotten.

TLM

Compare a point to point request path with an analysis broadcast. Say who calls the method and who implements it.

Factory

Give a real override example and explain why direct construction prevents it.

Configuration

Show how a virtual interface reaches an agent and how you debug a failed path match.

RAL

Explain model, map, adapter, predictor and mirrored value through one front door register write.

Bring up

State the order: topology, configuration, connectivity, one directed transfer, checking, then random pressure.

My interview rule: if you can follow one transaction and explain the first place it can go wrong, you understand more UVM than someone who memorized every callback.

Where AI helps verification, and where I do not trust it.

I work on AI assisted verification because the useful question is not whether a model can produce code. It is whether the result helps an engineer reach better evidence without hiding a mistake.

UVM bring up

Use AI to get past the blank file, not past review.

A model can sketch a transaction class, sequence or agent structure quickly. I find that useful when the interface contract is already clear.

The review still belongs to the engineer. I check factory registration, phase behavior, objections, reset handling, analysis connections and whether the monitor reports accepted traffic. Code that compiles can still encode the wrong architecture.

From my IEEE paper

Regression optimization is a ranking problem before it is an AI problem.

My work studied AI assisted regression optimization. In plain language, the goal is to spend simulation time on tests that are likely to add useful information, rather than treating every test as equally valuable.

The important part is the feedback loop. Test history, coverage movement and failure behavior have to be represented carefully. A model can help prioritize; it cannot decide that unobserved behavior is safe.

Failure modes

Fluent code is not the same as correct verification.

AI often produces something plausible before it produces something precise. It can invent signal names, misunderstand a reset convention, overconstrain random stimulus or write an assertion with the wrong cycle semantics.

I treat every generated line as an unreviewed suggestion. If I cannot explain what requirement it checks and make it fail on purpose, it does not belong in the bench.

A small rule from the lab

Ask the model to state its assumptions before it writes code. The assumptions are often more useful than the first answer, and they give you something concrete to challenge.

Five core DV interview questions to reason throughINTERVIEW PREP

I do not memorize a perfect answer. I use a simple shape: clarify the requirement, choose a mechanism, give one concrete example and name the evidence or tradeoff.

A sample answer

For “assertion or scoreboard,” I would say that an assertion suits a local timing rule such as grant within three cycles. A scoreboard suits an ordered result that needs prediction and state. On a bus agent I may use both because protocol legality and data correctness are different questions.

Key takeaway: the interviewer is listening for judgement. Show why you chose the technique and what you would inspect when it fails.

  1. When should a check be an assertion, a scoreboard comparison or both?
  2. What makes a constrained random test useful rather than merely random?
  3. How would you verify reset in the middle of active traffic?
  4. A regression fails once in one thousand seeds. How do you preserve and localize it?
  5. What does 100 percent functional coverage prove, and what does it not prove?
Specification extraction checklistSTRATEGY

I use this before writing a test plan. The goal is to separate stated behavior from assumptions and to expose the conditions that are easy to miss in normal traffic.

Practical example

For a FIFO, “supports simultaneous read and write” is incomplete. Ask whether it applies at empty and full, whether occupancy changes, what data appears on the output and when flags update. Each answer becomes either a test, an assertion or a coverage point.

Key takeaway: an unanswered question is safer in a review list than as silent behavior inside a reference model.

  1. List inputs, outputs and persistent state.
  2. Mark every clock and reset domain.
  3. Write legal state transitions and forbidden transitions.
  4. For each command, record acceptance, response latency and backpressure.
  5. Define behavior at empty, full, minimum, maximum and simultaneous events.
  6. Note what must remain unchanged when an action is rejected.
  7. Record unspecified cases as questions and assign an owner.
Race resistant clocked stimulusSYSTEMVERILOG

A clocking block declares when the testbench samples and drives interface signals relative to a clock event. That removes accidental dependence on simulator scheduling order and makes driver and monitor intent visible in the interface.

How I use it

The driver writes through clocking block outputs. The monitor reads clocking block inputs. I still decide the protocol timing explicitly. A clocking block prevents a race; it does not decide whether request should remain high until grant.

Key takeaway: consistent sampling removes testbench ambiguity, so a cycle mismatch is more likely to expose a real protocol misunderstanding.

clocking cb @(posedge clk);
  default input #1step output #0;
  output req, wdata;
  input  gnt, rdata;
endclocking

cb.req   <= 1'b1;
cb.wdata <= payload;
@cb;
if (cb.gnt) begin
  // The monitor sees a stable sampled value.
end
Check it deliberately: drive request near the active edge once without the clocking block and once through it. Compare which sampled value the DUT and monitor see.
Build phase and connect phaseUVM

I think of build as creating the testbench structure and connect as wiring communication after that structure exists. This is not ceremony. It gives structural failures a predictable place.

A useful debug order

If the scoreboard receives nothing, first print the topology. Then confirm the monitor exists and has the expected virtual interface. Next inspect the analysis port connection. Only after those checks should you debug transaction contents.

Key takeaway: prove hierarchy, configuration and connectivity before blaming run phase behavior.

  1. Build phase: create child components with the factory, read configuration and choose active or passive structure.
  2. Parent before child: the parent creates the children that UVM will build next.
  3. Connect phase: connect sequencer and driver paths, ports, exports and analysis paths.
  4. Topology check: confirm every expected component and instance name.
  5. Configuration check: verify the path used to set a virtual interface matches the path used to get it.
  6. Common mistake: using new for components removes useful factory override behavior.
An assertion sentence templateSVA

Say the requirement first: “When request rises, grant must arrive one to three cycles later, unless reset is active.” Then map the clock, reset, trigger, implication and response window one phrase at a time.

Boundary traces

Write four tiny waveforms before coding. Grant at one, two and three cycles must pass. Grant at four cycles must fail. Also test a request just before reset so you know whether the active attempt should be aborted.

Key takeaway: operators are easier to choose after the pass and fail boundaries are unambiguous.

property p_req_gets_grant;
  @(posedge clk)
  disable iff (!rst_n)
  $rose(req) |-> ##[1:3] grant;
endproperty

a_req_gets_grant:
  assert property (p_req_gets_grant);
Watch for vacuity: if request never rises, this property can pass without testing the response. Add coverage for the trigger and successful completion.
Coverage hole triageCLOSURE

Do not write a new random test until you know what kind of hole you are looking at. Start with one uncovered bin and trace the evidence from stimulus to accepted interface event to monitor sample.

Practical example

Suppose the cross of full, read and write is empty. A transaction log may show both commands were generated, while the interface trace shows read was blocked before acceptance. That is a stimulus or sequencing issue, not a covergroup issue.

Key takeaway: coverage closure is an investigation. The outcome can be a new test, a monitor fix, a model correction, a design bug or a justified exclusion.

  • Stimulus hole: a legal scenario was never accepted. Adjust constraints or write a focused sequence.
  • Observability hole: the scenario happened but the monitor or covergroup missed it.
  • Model hole: the bin does not represent a real requirement. Repair the model.
  • Unreachable hole: prove the condition cannot occur, then document the exclusion.
  • Design hole: intended behavior cannot be reached because the RTL is wrong.
  • Review question: would hitting this bin add evidence, or only improve the percentage?
CDC structure chooserCDC

A synchronizer does not make CDC safe in general. First name what crosses and what the destination must preserve. Then choose a structure and verify its protocol assumptions.

Practical example

A one cycle pulse from a 200 MHz source can fall entirely between edges of a 50 MHz destination. Two flops reduce metastability risk only if an edge samples the level. A toggle converts the event into a persistent state change; a handshake also provides backpressure when events may arrive quickly.

Key takeaway: metastability, event loss, incoherent data and reconvergence are related but different failure modes.

  • Stable single bit level: use a multi flip flop synchronizer and verify the source stays stable long enough.
  • Brief event: stretch, toggle or handshake so the destination cannot miss it.
  • Multi bit control: preserve relationships between bits and analyze reconvergence.
  • Ordered payload: use a handshake or asynchronous FIFO with control synchronized separately.
  • Reset crossing: asynchronous assertion may be required, but deassertion must be controlled in each domain.
  • Verification check: vary clock ratio and phase, then check for loss, duplication and reordering.
VIII

Build sound judgement through deliberate practice.

Use a small design whose state you can predict by hand. A counter, arbiter or tiny FIFO is enough. The aim is not merely a green test. It is a clear argument that the design satisfies its intent and a debug trail that tells you why it does not.

My favorite exercise is a depth four FIFO with one intentional bug. I write the expected occupancy and pointer values for each cycle before I open the waveform. That forces me to reason from the protocol instead of searching visually for anything unusual.

Keep the design small until the reasoning becomes automatic. Complexity can hide weak checking. A ten signal block with a precise testbench teaches more than a large subsystem where success means only that simulation finished.

01
PredictWrite the expected state transition, accepted transaction and output before simulation. If you cannot predict it, clarify the requirement first.
02
BreakIntroduce one fault or choose one boundary on purpose. Keep every other variable quiet so the result remains explainable.
03
ObserveDecide which assertion, monitor or scoreboard comparison should detect the fault and on which cycle.
04
ExplainWrite the first bad cycle, expected behavior, observed behavior and likely cause in one precise paragraph.

A forty five minute FIFO practice session

Minutes 0 to 10Write the contract

Define depth, reset values, flag timing and the behavior of simultaneous read and write at empty and full.

Minutes 10 to 20Build one clean check

Maintain a queue as the expected model. Add data only on an accepted write and remove data only on an accepted read.

Minutes 20 to 35Attack one boundary

Fill to capacity, attempt overflow, read everything back and confirm the rejected value never appears.

Minutes 35 to 45Break and explain

Delay the full flag or allow one extra pointer increment. Predict the first failing cycle, run once and compare your prediction.

Keep a verification ledger

For each session, save the requirement, your prediction, the checker that fired and the final root cause. This becomes a much better study record than a folder of code that once passed.

  • Requirement: what behavior were you trying to prove?
  • Failure injected: what changed in the RTL or stimulus?
  • First bad cycle: where did expected and observed behavior diverge?
  • Detection: which checker caught it, and did it report enough context?
  • Next improvement: what assumption or visibility gap did the exercise reveal?

Key takeaway: practice is complete when you can predict, detect and explain the failure. Passing the clean design is only the starting point.
