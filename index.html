Verification term of the day

Observability

How easily an internal behavior can be seen at an output, monitor or checker. If a bug happens but nothing notices, you do not have enough observability.

A structured path through design verification.

You do not need to master every language feature before verifying a block. Begin with the path that best matches the work in front of you.

Verification foundations

A beginner’s guide to design verification.

If you are new to the field, work through these modules in order. Learn enough to build one small testbench, then return to the earlier lessons with the questions that practical work brings.

You finished the roadmap. Nice work. Your reward is the most verification shaped compliment I know: your assumptions are now observable.

  1. What verification engineers actually do

    Begin with the job

    Design engineers build the RTL. Verification engineers build the evidence that the RTL behaves as intended, including at boundaries and under failure conditions. The role exists because a design can compile and still be wrong.

    1. Learn how a requirement becomes a verification plan.
    2. Separate stimulus, observation, checking and coverage.
    3. Understand the difference between a design bug and a testbench bug.
    ExampleA FIFO write on the same cycle as reset is not just a corner case. The specification must say which action wins.
    Common mistakeWriting tests before deciding what the checker can actually observe.
    PracticeTake one page of a specification and list five behaviors, three boundaries and two unanswered questions.

  2. Digital design foundations

    Read the hardware first

    You need enough digital design knowledge to predict what the DUT should do. Start with the behavior you can see at a clock edge, not transistor physics.

    1. Boolean logic, combinational logic and sequential logic.
    2. Flip flops, registers, counters and finite state machines.
    3. Clocks, reset, setup and hold, latency and throughput.
    4. Basic buses, valid and ready handshakes, FIFO empty and full behavior.
    ExampleIf valid stays high while ready is low, the payload normally has to remain stable until the transfer happens.
    Common mistakeTreating a waveform as decoration instead of tracing state one clock edge at a time.
    PracticeDraw a four cycle handshake by hand and mark exactly when the transfer is accepted.

  3. SystemVerilog for verification

    Learn the language in context

    SystemVerilog is both a design language and a verification language. For DV, learn the parts that help you represent transactions, generate varied stimulus and coordinate concurrent work.

    1. Types, arrays, queues, structs and interfaces.
    2. Tasks, functions, classes and object handles.
    3. Processes, events, mailboxes and clocking blocks.
    4. Randomization, constraints and why a legal random space matters.
    ExampleA queue makes sense for an ordered stream of transactions because its size can grow and items can be popped in order.
    Common mistakeJumping into classes before understanding blocking, nonblocking and event scheduling.
    PracticeModel a packet with a class, constrain its length and print ten legal variations.

  4. Testbench thinking

    Build a checking loop

    Before UVM, write one small testbench. Drive known inputs, observe the output and compare it with an expected result. This makes the later UVM structure feel necessary instead of ceremonial.

    1. Write a test plan from a small specification.
    2. Create a transaction and a simple reference model.
    3. Drive the interface and monitor what the DUT accepted.
    4. Make failures clear enough that another engineer can debug them.
    ExampleFor an adder, generate operands, predict the sum independently and report the inputs with every mismatch.
    Common mistakeCalling a test successful because the waveform looks reasonable.
    PracticeVerify a counter with reset, enable, wraparound and one deliberately broken RTL version.

  5. UVM from scratch

    Structure first, then behavior

    UVM organizes work you already understand. Learn it in the order the testbench comes to life.

    1. Build phase: create components and read configuration.
    2. Connect phase: wire ports and exports once components exist.
    3. Run phase: let simulation time advance and manage objections.
    4. Agent: group a sequencer, driver and monitor for one interface.
    5. Driver and monitor: translate transactions to pins and pins back to transactions.
    6. Sequences: describe stimulus intent without pin level detail.
    7. Scoreboard: compare observed results with a prediction.
    ExampleA monitor should report what the DUT accepted, not what the driver hoped it sent.
    Common mistakeLearning component names without following one transaction through the entire bench.
    PracticeDraw sequence, sequencer, driver, monitor and scoreboard. Label every transaction path.
    Recommended:UVM build and connect phase series

  6. SystemVerilog assertions

    Make timing rules executable

    Assertions are compact checkers for behavior over time. Start by turning one English sentence into a trigger, a timing window and a required response.

    1. Immediate and concurrent assertions.
    2. Sequences, properties and sampled values.
    3. Overlapped and nonoverlapped implication.
    4. Delay ranges, repetition and reset with disable iff.
    Example“Request implies grant within three cycles” needs a precise decision about whether the current cycle counts.
    Common mistakeWriting one giant property that fails without telling you which rule broke.
    PracticeTranslate three English timing rules, then fail each property on purpose.
    Recommended:Top 5 SVA questions and answers in the interview hub

  7. CDC basics

    Preserve information across clocks

    A clock domain crossing problem is not only about metastability. The destination must receive the same information the source intended to send.

    1. Understand metastability and why simulation alone cannot model it fully.
    2. Use a synchronizer for a stable single bit level.
    3. Use a pulse, toggle or handshake scheme for events.
    4. Use an asynchronous FIFO for a data stream.
    5. Learn why multi bit reconvergence needs separate attention.
    ExampleA slow destination can miss a one cycle pulse even when metastability is handled.
    Common mistakeAdding two flops to every crossing without asking what information must survive.
    PracticeClassify a level, pulse, counter and data stream, then choose a structure for each.

  8. Functional coverage and signoff

    Ask whether the evidence is enough

    Coverage tells you what your tests exercised. It does not prove correctness by itself. Use it with assertions, checking, code coverage and bug review to decide what remains unknown.

    1. Write coverpoints for behaviors in the verification plan.
    2. Add crosses only when the combination has meaning.
    3. Classify holes as stimulus, observability, model, unreachable or design gaps.
    4. Review checks, coverage, bugs and waivers before signoff.
    ExampleA missed bin may mean the stimulus never reached a legal case, or that the bin itself describes something impossible.
    Common mistakeTreating 100 percent as proof that every checked behavior is correct.
    PracticePick five coverage holes and classify each before changing a constraint.

  9. Interview preparation

    Explain your reasoning out loud

    An interview answer is stronger when you can explain why a method exists, where it fails and how you would debug it. Practice on paper and speak through one transaction from sequence to scoreboard.

    1. Review digital design and SystemVerilog fundamentals.
    2. Draw UVM data flow and phase order without notes.
    3. Write one assertion from an English requirement.
    4. Explain one real debug method from first failure to root cause.
    5. Answer with a small example, then name the tradeoff.
    ExampleFor every “what is” question, add a “when would you use it” and a “what can go wrong.”
    Common mistakeReciting a definition and stopping before the interviewer can hear your judgement.
    PracticeRecord a two minute answer, listen once and remove every sentence that does not help the reasoning.
    Recommended:DV core interview questions

III
A worked example

Turning one requirement into a useful test.

Take a requirement such as “a full FIFO must reject writes without corrupting stored data.” I do not begin by opening a sequence file. I first turn that sentence into four things I can reason about: the starting state, the action, the visible response and the state that must not change.

The phrase “reject writes” is not precise enough on its own. Does the interface lower ready, raise an error or accept the handshake and discard the data? Does the full flag rise on the same edge as the final legal write or one cycle later? Those questions belong in the specification discussion, not in a guess hidden inside the scoreboard.

The concrete test

Use a depth four FIFO and write A, B, C and D. Check that full asserts at the specified time. While full, attempt to write X. Then read four entries and expect A, B, C and D in order, followed by empty. X must never appear, and neither pointer may advance for the rejected transfer.

If it fails

Start at the first bad cycle. If the write pointer moved, the acceptance rule is wrong. If the pointer stayed still but a later read returns X, inspect the memory write enable. If data is correct but full is late, the flag calculation may use stale pointer state. One requirement can expose several distinct bugs.

Name the behaviorA write attempted while full must not become a stored transaction.Question to ask: what exact interface event counts as an attempt?

Control the preconditionFill the FIFO to its declared capacity with recognizable values.Example: A, B, C and D make ordering errors obvious.

Apply one meaningful actionAttempt one additional write and keep all unrelated controls quiet.Changing only one thing makes the result easier to diagnose.

Check response and invariantsCheck the interface response, pointer stability, occupancy and eventual readback.The full flag is one observation, not the whole proof.

Record the evidenceCover full with a write attempt and assert that rejected writes do not change state.Also retain the directed readback because it checks data integrity.

Key takeaway: a good test proves both the visible response and the invariants behind it. If the requirement leaves cycle timing or acceptance semantics unclear, resolve that before encoding the answer in the testbench.

DV core interview questions

These questions are less about recalling definitions and more about showing how you make a verification decision. A useful answer starts with the requirement, names the checker or stimulus mechanism and finishes with the evidence you would inspect.

Try this: explain reset during traffic for a request and response interface. State what happens to an accepted request, how the monitor recognizes reset and how the scoreboard removes stale expectations.

Keep: definition, example, tradeoff and debug step. That four part answer is usually stronger than a long list of terms.

Top 5 SVA questions and answers

Assertion syntax becomes much easier when every property is first written as a clocked sentence. Identify the trigger, decide whether the response may happen now or later, define the allowed window and say what reset does to an active attempt.

Try this: compare |-> and |=> by drawing the trigger at cycle 10. If the response must be true on cycle 10, use overlapped implication. If the earliest legal response is cycle 11, use nonoverlapped implication.

Keep: never trust a property until you have seen it pass for the right reason and fail on the intended bad trace.

Write assertions from English

One property should communicate one timing rule. Split compound requirements so a failure points toward a specific cause. Reset handling also needs to match intent: aborting a property and requiring a reset value are two different checks.

Try this: for “request gets grant within one to three cycles,” create separate traces where grant arrives at cycles one, two, three and four. The first three should pass. The fourth should fail.

Keep: write the boundary traces before the property. They force vague timing language to become precise.

CoverageClosure

Classify a coverage hole

An uncovered bin is a question, not an instruction to run more seeds. The scenario may be legal but ungenerated, generated but invisible, impossible by design or missing because the RTL cannot reach the intended state.

Try this: if full and simultaneous read plus write is uncovered, first prove the FIFO reached full, then confirm the monitor sampled both controls on the acceptance edge. Only after that should you change stimulus.

Keep: every hole should end with an owner and a reason, not merely a new test name.

CDCStructures

Choose the crossing by information type

The crossing structure depends on what must survive: a stable level, a brief event, a related group of bits or an ordered stream. A pair of synchronizer flops addresses metastability risk for a sampled control, but it does not preserve every kind of information.

Try this: send a one cycle source pulse into a slower destination clock. If no destination edge sees the pulse, two flops cannot recover it. A toggle or handshake carries the event instead.

Keep: ask what information the destination must receive before choosing the circuit that crosses it.

Interview practice that tests how you think.

A strong answer is not a wall of terminology. I listen for a clear model, one useful example and an honest tradeoff. These are the questions I would use to practise that habit.

When should a check live in an assertion, a scoreboard or both?

I use an assertion when the rule is local in time and tied closely to an interface or protocol. “Grant arrives within three cycles of request” is a good assertion. I use a scoreboard when the expected result needs state, ordering or a reference model.

Sometimes both are right. The assertion checks that the protocol stayed legal while the scoreboard checks the end result. I would say that out loud, then give one failure each checker can catch.

How would you verify reset in the middle of active traffic?

I would first ask what the specification promises. Are outstanding transactions dropped, replayed or completed? Which outputs must change immediately and which change on a clock edge?

Then I would reset at different points in a transaction, check state cleanup, confirm no stale response escapes and verify the first legal transaction after reset. The common mistake is checking only that registers become zero. Reset is a behavior, not just a value.

A random regression fails once in one thousand seeds. What do you do first?

I preserve the seed, tool version, configuration and first failing message before changing anything. Then I reproduce the smallest failing run and work backwards from the first bad observation, not from the final scoreboard complaint.

I also compare the failing and passing traces near the divergence. Adding debug everywhere too early can make the failure slower to understand. One precise hypothesis at a time usually wins.

What does 100 percent functional coverage prove?

It proves that every modeled bin was sampled. That is useful, but it does not prove the model was complete, the checker was correct or the design behaved properly when the bin was hit.

I would review the coverage model against the verification plan, look at meaningful crosses, inspect assertion results and close known bug and waiver questions. A full dashboard can still hide a weak argument.

How do you debug a scoreboard mismatch?

I start with the earliest mismatch and ask four things: was the input transaction observed correctly, did the reference model predict the right value, did the output monitor sample the right cycle and did the queue preserve ordering?

Only then do I blame the DUT. Scoreboards are excellent at reporting disagreement, but they do not automatically tell us which side is wrong. That distinction matters in real debug.

Where AI helps verification, and where I do not trust it.

I work on AI assisted verification because the useful question is not whether a model can produce code. It is whether the result helps an engineer reach better evidence without hiding a mistake.

UVM bring up

Use AI to get past the blank file, not past review.

A model can sketch a transaction class, sequence or agent structure quickly. I find that useful when the interface contract is already clear.

The review still belongs to the engineer. I check factory registration, phase behavior, objections, reset handling, analysis connections and whether the monitor reports accepted traffic. Code that compiles can still encode the wrong architecture.

From my IEEE paper

Regression optimization is a ranking problem before it is an AI problem.

My work studied AI assisted regression optimization. In plain language, the goal is to spend simulation time on tests that are likely to add useful information, rather than treating every test as equally valuable.

The important part is the feedback loop. Test history, coverage movement and failure behavior have to be represented carefully. A model can help prioritize; it cannot decide that unobserved behavior is safe.

Failure modes

Fluent code is not the same as correct verification.

AI often produces something plausible before it produces something precise. It can invent signal names, misunderstand a reset convention, overconstrain random stimulus or write an assertion with the wrong cycle semantics.

I treat every generated line as an unreviewed suggestion. If I cannot explain what requirement it checks and make it fail on purpose, it does not belong in the bench.

A small rule from the lab

Ask the model to state its assumptions before it writes code. The assumptions are often more useful than the first answer, and they give you something concrete to challenge.

Five core DV interview questions to reason throughINTERVIEW PREP

I do not memorize a perfect answer. I use a simple shape: clarify the requirement, choose a mechanism, give one concrete example and name the evidence or tradeoff.

A sample answer

For “assertion or scoreboard,” I would say that an assertion suits a local timing rule such as grant within three cycles. A scoreboard suits an ordered result that needs prediction and state. On a bus agent I may use both because protocol legality and data correctness are different questions.

Key takeaway: the interviewer is listening for judgement. Show why you chose the technique and what you would inspect when it fails.

  1. When should a check be an assertion, a scoreboard comparison or both?
  2. What makes a constrained random test useful rather than merely random?
  3. How would you verify reset in the middle of active traffic?
  4. A regression fails once in one thousand seeds. How do you preserve and localize it?
  5. What does 100 percent functional coverage prove, and what does it not prove?
Specification extraction checklistSTRATEGY

I use this before writing a test plan. The goal is to separate stated behavior from assumptions and to expose the conditions that are easy to miss in normal traffic.

Practical example

For a FIFO, “supports simultaneous read and write” is incomplete. Ask whether it applies at empty and full, whether occupancy changes, what data appears on the output and when flags update. Each answer becomes either a test, an assertion or a coverage point.

Key takeaway: an unanswered question is safer in a review list than as silent behavior inside a reference model.

  1. List inputs, outputs and persistent state.
  2. Mark every clock and reset domain.
  3. Write legal state transitions and forbidden transitions.
  4. For each command, record acceptance, response latency and backpressure.
  5. Define behavior at empty, full, minimum, maximum and simultaneous events.
  6. Note what must remain unchanged when an action is rejected.
  7. Record unspecified cases as questions and assign an owner.
Race resistant clocked stimulusSYSTEMVERILOG

A clocking block declares when the testbench samples and drives interface signals relative to a clock event. That removes accidental dependence on simulator scheduling order and makes driver and monitor intent visible in the interface.

How I use it

The driver writes through clocking block outputs. The monitor reads clocking block inputs. I still decide the protocol timing explicitly. A clocking block prevents a race; it does not decide whether request should remain high until grant.

Key takeaway: consistent sampling removes testbench ambiguity, so a cycle mismatch is more likely to expose a real protocol misunderstanding.

clocking cb @(posedge clk);
  default input #1step output #0;
  output req, wdata;
  input  gnt, rdata;
endclocking

cb.req   <= 1'b1;
cb.wdata <= payload;
@cb;
if (cb.gnt) begin
  // The monitor sees a stable sampled value.
end
Check it deliberately: drive request near the active edge once without the clocking block and once through it. Compare which sampled value the DUT and monitor see.
Build phase and connect phaseUVM

I think of build as creating the testbench structure and connect as wiring communication after that structure exists. This is not ceremony. It gives structural failures a predictable place.

A useful debug order

If the scoreboard receives nothing, first print the topology. Then confirm the monitor exists and has the expected virtual interface. Next inspect the analysis port connection. Only after those checks should you debug transaction contents.

Key takeaway: prove hierarchy, configuration and connectivity before blaming run phase behavior.

  1. Build phase: create child components with the factory, read configuration and choose active or passive structure.
  2. Parent before child: the parent creates the children that UVM will build next.
  3. Connect phase: connect sequencer and driver paths, ports, exports and analysis paths.
  4. Topology check: confirm every expected component and instance name.
  5. Configuration check: verify the path used to set a virtual interface matches the path used to get it.
  6. Common mistake: using new for components removes useful factory override behavior.
An assertion sentence templateSVA

Say the requirement first: “When request rises, grant must arrive one to three cycles later, unless reset is active.” Then map the clock, reset, trigger, implication and response window one phrase at a time.

Boundary traces

Write four tiny waveforms before coding. Grant at one, two and three cycles must pass. Grant at four cycles must fail. Also test a request just before reset so you know whether the active attempt should be aborted.

Key takeaway: operators are easier to choose after the pass and fail boundaries are unambiguous.

property p_req_gets_grant;
  @(posedge clk)
  disable iff (!rst_n)
  $rose(req) |-> ##[1:3] grant;
endproperty

a_req_gets_grant:
  assert property (p_req_gets_grant);
Watch for vacuity: if request never rises, this property can pass without testing the response. Add coverage for the trigger and successful completion.
Coverage hole triageCLOSURE

Do not write a new random test until you know what kind of hole you are looking at. Start with one uncovered bin and trace the evidence from stimulus to accepted interface event to monitor sample.

Practical example

Suppose the cross of full, read and write is empty. A transaction log may show both commands were generated, while the interface trace shows read was blocked before acceptance. That is a stimulus or sequencing issue, not a covergroup issue.

Key takeaway: coverage closure is an investigation. The outcome can be a new test, a monitor fix, a model correction, a design bug or a justified exclusion.

  • Stimulus hole: a legal scenario was never accepted. Adjust constraints or write a focused sequence.
  • Observability hole: the scenario happened but the monitor or covergroup missed it.
  • Model hole: the bin does not represent a real requirement. Repair the model.
  • Unreachable hole: prove the condition cannot occur, then document the exclusion.
  • Design hole: intended behavior cannot be reached because the RTL is wrong.
  • Review question: would hitting this bin add evidence, or only improve the percentage?
CDC structure chooserCDC

A synchronizer does not make CDC safe in general. First name what crosses and what the destination must preserve. Then choose a structure and verify its protocol assumptions.

Practical example

A one cycle pulse from a 200 MHz source can fall entirely between edges of a 50 MHz destination. Two flops reduce metastability risk only if an edge samples the level. A toggle converts the event into a persistent state change; a handshake also provides backpressure when events may arrive quickly.

Key takeaway: metastability, event loss, incoherent data and reconvergence are related but different failure modes.

  • Stable single bit level: use a multi flip flop synchronizer and verify the source stays stable long enough.
  • Brief event: stretch, toggle or handshake so the destination cannot miss it.
  • Multi bit control: preserve relationships between bits and analyze reconvergence.
  • Ordered payload: use a handshake or asynchronous FIFO with control synchronized separately.
  • Reset crossing: asynchronous assertion may be required, but deassertion must be controlled in each domain.
  • Verification check: vary clock ratio and phase, then check for loss, duplication and reordering.
VIII

Build sound judgement through deliberate practice.

Use a small design whose state you can predict by hand. A counter, arbiter or tiny FIFO is enough. The aim is not merely a green test. It is a clear argument that the design satisfies its intent and a debug trail that tells you why it does not.

My favorite exercise is a depth four FIFO with one intentional bug. I write the expected occupancy and pointer values for each cycle before I open the waveform. That forces me to reason from the protocol instead of searching visually for anything unusual.

Keep the design small until the reasoning becomes automatic. Complexity can hide weak checking. A ten signal block with a precise testbench teaches more than a large subsystem where success means only that simulation finished.

01
PredictWrite the expected state transition, accepted transaction and output before simulation. If you cannot predict it, clarify the requirement first.
02
BreakIntroduce one fault or choose one boundary on purpose. Keep every other variable quiet so the result remains explainable.
03
ObserveDecide which assertion, monitor or scoreboard comparison should detect the fault and on which cycle.
04
ExplainWrite the first bad cycle, expected behavior, observed behavior and likely cause in one precise paragraph.

A forty five minute FIFO practice session

Minutes 0 to 10Write the contract

Define depth, reset values, flag timing and the behavior of simultaneous read and write at empty and full.

Minutes 10 to 20Build one clean check

Maintain a queue as the expected model. Add data only on an accepted write and remove data only on an accepted read.

Minutes 20 to 35Attack one boundary

Fill to capacity, attempt overflow, read everything back and confirm the rejected value never appears.

Minutes 35 to 45Break and explain

Delay the full flag or allow one extra pointer increment. Predict the first failing cycle, run once and compare your prediction.

Keep a verification ledger

For each session, save the requirement, your prediction, the checker that fired and the final root cause. This becomes a much better study record than a folder of code that once passed.

  • Requirement: what behavior were you trying to prove?
  • Failure injected: what changed in the RTL or stimulus?
  • First bad cycle: where did expected and observed behavior diverge?
  • Detection: which checker caught it, and did it report enough context?
  • Next improvement: what assumption or visibility gap did the exercise reveal?

Key takeaway: practice is complete when you can predict, detect and explain the failure. Passing the clean design is only the starting point.
